### D51 本地一键质量门禁（2026-10-23）

- **背景**：批次工作流要求单测 → lint → release，但此前依赖人工逐条执行，容易漏跑或漏记测试数、lint 数、APK 大小；Windows PowerShell 5.1 直接输出中文可能乱码。
- **决策**：
  1. 新增 `scripts/verify.ps1`，固定顺序执行 `testDebugUnitTest`、`lintDebug`、`assembleRelease`，并在最后解析 JUnit XML、lint txt 与 APK 字节数。
  2. 脚本输出保持英文，避免 PowerShell 5.1 控制台编码问题；任一步失败或 lint error > 0 时以非 0 退出。
  3. 脚本不安装 APK、不启动模拟器、不跑 `androidTest`；模拟器走查仍是独立必做步骤。
  4. 批次汇报必须记录脚本输出的测试数、lint errors/warnings 与 APK 大小。
- **理由 / 取舍**：把可自动化的门禁收口到一个命令，减少“忘记跑 lint / 没记录大小”；不引入 CI 与额外依赖，保持本机可跑。英文输出牺牲中文可读性，换取跨 PowerShell 版本的稳定性。
- **影响范围**：工程脚本与文档；不改应用代码、构建配置或产物。
- **验证方式**：在仓库根目录运行 `.\scripts\verify.ps1`，输出 `VERIFY PASSED`；基线随批次更新，M13-3 起为 269/269 测试、lint 0 errors / 0 warnings、release APK 2,231,460 bytes（以脚本实际输出为准）。

### D53 跨逻辑日可见时钟：≤60s 轮询，逻辑日变化才刷新（2026-11-02）

- **背景**：各页只在 `LifecycleResumeEffect` 回前台时刷新逻辑日，App 长驻前台跨过「新的一天开始于」（默认凌晨 4 点）时，今日 / 日历 / 日期详情 / 统计仍显示旧日期，直到用户切页或回前台（技术债 P1）。
- **决策**：
  1. 新增 `domain/time/LogicalDayTicker.kt`：纯函数 `logicalDayDelayMillis`（到下一边界的睡眠时长，下限 1s、上限 60s）+ 挂起函数 `watchLogicalDay(settingsOf, onNewDay)`。
  2. 今日 / 日历 / 日期详情 / 统计 4 个 ViewModel 的 `init` 启动该循环，逻辑日变化才调用各自的 `refreshToday()` / `refresh()`；协程随 `viewModelScope` 取消。
  3. 保留各页 `LifecycleResumeEffect` 回前台刷新；小组件仍按 D41 的系统 30 分钟周期，不接轮询。
- **理由 / 取舍**：一次睡到边界（约数小时）无法自愈改时区、改「新的一天开始于」、系统改时等事件，60s 轮询每次只读一次设置，功耗可忽略；不引入 AlarmManager / 前台服务。代价是每页常驻一个轻量协程。
- **影响范围**：4 个 ViewModel 与新增 domain 文件；不改 schema、备份/CSV、权限、依赖。
- **验证方式**：`LogicalDayTickerTest` 5 例（边界前 30 秒、整点跨界按上限截断、自定义上限、边界已过按下限唤醒、夏令时 23 小时日）；模拟器保持在今日页不切页，把系统时间拨到边界前 30 秒，跨点后日期标签自动从「11月2日」变「11月3日」，截图 `docs/截图/m13-01-logical-day-before/after.png`。

### D54 「稍后」用 SharedPreferences 持久化并在重排时恢复（2026-11-02）

- **背景**：「稍后」排的是 `AlarmManager` 一次性闹钟，设备重启后被系统清空，而 `ReminderBootReceiver` 只重排系列提醒，不恢复稍后（技术债 P3）。
- **决策**：
  1. 新增 `reminder/SnoozeStore`：应用私有 SharedPreferences（`snooze_prefs`），存 `reminderId → (itemId, triggerAtMillis)`。
  2. `ReminderScheduler.scheduleSnooze` 写入、`cancel` 与 `clearSnooze` 删除；`ReminderReceiver` 在稍后闹钟触发时先清除记录再做校验。
  3. `rescheduleAll()`（开机 / 改时间 / 改时区 / 应用更新 / 启动）末尾 `restoreSnoozes()`：提醒或选项无效、暂停中、已过期的记录清除，未到期的按原 `triggerAt` 重排。
- **理由 / 取舍**：稍后是瞬态排期（最长 24 小时、过期即失效），不是用户数据——用 SharedPreferences 可以**不改 Room schema、不进备份、不加迁移**；代价是它不随备份导出（可接受：换机导入后备份里的稍后本就无意义）。备选方案（AppSettings 加字段）需要 v6→v7 迁移与备份格式变更，成本不成比例。
- **影响范围**：`reminder/` 三个文件 + `ReminderSchedulerTest` 4 例；不改 schema、备份 / CSV、权限、依赖。
- **验证方式**：单测覆盖写入 / 取消清除、重启后按原时刻恢复、过期清除、暂停期间不恢复；模拟器实测——提醒到点后点「稍后 10 分钟」→ `adb reboot` → `dumpsys alarm` 显示 `REMINDER_FIRE_SNOOZE` 的 `origWhen` 与重启前一致 → 到点再次弹出通知，截图 `docs/截图/m13-02-snooze-scheduled.png`、`m13-02-snooze-after-reboot.png`。

- **背景**：技术债「依赖版本新旧混杂」与 lint 的 6 条 `GradleDependency`（core-ktx 1.10.1→1.18.0、lifecycle 2.8.7→2.11.0、activity-compose 1.8.0→1.13.0）和 1 条 `NewerVersionAvailable`（Kotlin/Compose 插件 2.2.10→2.4.21）。

  1. 只把 AndroidX 三个库升到 lint 提示的稳定版本；Kotlin、KSP、AGP、Compose BOM、Room 一律不动。
  2. Kotlin 插件的新版本提示用 `app/lint.xml`（`NewerVersionAvailable` severity=ignore）压掉，其余 lint 规则照常暴露。
  3. 顺带移除全库无引用的 `androidx.datastore-preferences` 依赖（设置一直存 Room `AppSettings`，该依赖是历史遗留死依赖）。

- **影响范围**：`gradle/libs.versions.toml`、`app/build.gradle.kts`、`app/lint.xml`；不改业务代码、schema、备份 / CSV、权限。
- **验证方式**：`.\scripts\verify.ps1` → `VERIFY PASSED`（269/269 测试、lint 0 errors / 0 warnings、release APK 2,231,460 bytes）；release 构建成功并覆盖安装冒烟。

  1. 生成自建 keystore：`keystore/daily_trace-release.jks`（PKCS12 / RSA 4096 / 10000 天 / alias `daily_trace` / `CN=Daily Trace, O=Daily Trace, C=CN`）；证书 SHA-256 `aba3c3eca6492c3b7ce7d41700d912204fd6b02e9f826346c66a19f69b10391c`。
  2. 签名参数从仓库根 `keystore.properties` 读取；`keystore/` 与 `keystore.properties` 均被 `.gitignore` 忽略，口令只存本机。
  3. 缺失 `keystore.properties` 时，所有 release 任务（`assembleRelease` / `bundleRelease` / `assemble` / `build` / `bundle`）在 configuration 阶段 `throw GradleException`，**不回退 debug 签名**；单测、lint、debug 构建不受影响。
  4. CI 不持有正式私钥，每次运行生成一次性 keystore，仅验证 release 可签名构建。
  5. 版本号规则写入 `docs/发布流程.md`：`versionCode` 单调递增，首个公开包建议直接到 10000（`1.0.0`），此后 `major*10000+minor*100+patch`。
- **理由 / 取舍**：早期失败比产出假签名包更安全；判断 release 任务用 `gradle.startParameter.taskNames`，实现最小，缺点是新增入口任务若命名不含 Release 需同步规则。keystore 入库虽方便 CI，但一旦泄露等同永久失去签名控制权，因此选择本机保管 + 强制备份。
- **影响范围**：`app/build.gradle.kts`、`.gitignore`、`docs/发布流程.md`、`docs/使用手册.md`、`docs/常见问题.md`、`docs/项目状态与计划.md`、`AGENTS.md`；不改业务代码、schema、权限。
- **验证方式**：`assembleRelease` 成功；`apksigner verify --print-certs` 输出 `CN=Daily Trace, O=Daily Trace, C=CN`；临时移除 `keystore.properties` 后 `assembleRelease` 以明确错误失败、`testDebugUnitTest --dry-run` 仍成功。

### D58 权限口径：自声明 3 项 + WorkManager 传递 3 项 + 自动生成 1 项（2026-11-09）

- **背景**：基线体检用 `aapt2 dump permissions` 核对发布包，发现合并后 Manifest 实际含 7 条权限，而 `docs/项目状态与计划.md`、`docs/隐私与数据安全.md`、`AGENTS.md` 第 11 条均声称「仅 3 项」，其中隐私文档还明确写「未申请 `ACCESS_NETWORK_STATE`」。
- **决策**：以构建产物为准重新定义口径：
  - 自声明：`POST_NOTIFICATIONS`、`SCHEDULE_EXACT_ALARM`、`RECEIVE_BOOT_COMPLETED`；
  - `androidx.work:work-runtime:2.12.0` 传递引入：`WAKE_LOCK`、`ACCESS_NETWORK_STATE`、`FOREGROUND_SERVICE`；
  - AndroidX 自动生成：`com.gh.daily_trace.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`；
  - 仍然**没有 `INTERNET`**，应用无法发起网络请求；新增任何自声明权限、或引入会带来新权限的依赖，必须先登记决策。
- **理由 / 取舍**：保留 WorkManager 的每日汇总能力（D40），避免为消除 3 条传递权限而维护自定义调度或 `tools:node="remove"`（后者需重新验证约束与重试行为）；以文档如实披露替代最小权限裁剪是可接受的取舍。
- **影响范围**：`AGENTS.md` 第 11 条、`docs/隐私与数据安全.md`、`docs/项目状态与计划.md`；`.github/workflows/quality-gate.yml` 以 `INTERNET` 作为硬门禁。
- **验证方式**：`aapt2 dump permissions app-release.apk` 输出与上述 7 条一致且无 `INTERNET`；CI 步骤 `Reject INTERNET permission` 对含 `INTERNET` 的权限串返回非 0。

> 注：本节「仍然没有 `INTERNET`」的结论已被 D59 取代；自声明权限由 3 项变为 4 项。

### D59 接受有限的联网能力：仅用于更新检查（2026-11-11）

- **背景**：应用发布后没有分发渠道之外的通知手段，用户无法得知新版本；完全离线的代价是补丁与新功能只能靠用户主动回访仓库。同时「不联网」是 README 的核心卖点之一，改动必须可解释、可验证、可回退。
- **决策**：
  - 只新增自声明权限 `INTERNET`；不申请「安装未知应用」，不引入第三方网络依赖（用 `HttpURLConnection`，请求放在 IO 协程）。
  - 访问范围仅限 GitHub：`https://api.github.com/repos/guohong-gh/daily_trace/releases/latest` 读取 `tag_name`；「去更新」用 `ACTION_VIEW` 打开 `https://github.com/guohong-gh/daily_trace/releases/latest`。
  - 不做应用内下载与安装：安装包仍由用户从浏览器获取并手动安装，应用只负责提示与跳转。
  - 冷启动后台检查一次，不阻塞首屏；同一版本只自动提示一次（`UpdateStore` 记录 `lastPromptedVersion`），远端出现更高版本时重新允许提示；设置页手动检查不受节流限制。
  - 请求只带固定 `User-Agent`（`DailyTrace/<versionName>`）与 `Accept`，不带设备标识、口令、打卡内容或备份数据；任何失败（断网、超时、限流、解析异常）静默并记录日志。
  - CI 由「出现 `INTERNET` 即失败」改为「必须声明 `INTERNET`，且 `app/src/main/java` 中的 http(s) 主机必须落在 `api.github.com`、`github.com` 白名单内，越界即失败」。
- **理由 / 取舍**：
  - 只用 GitHub 官方 API，不引入统计、推送或广告 SDK，联网面最小且可审计；版本号是公开信息，不含用户数据。
  - 节流避免每次冷启动都打扰用户；「稍后」保留手动入口，符合非强制更新的定位。
  - 不做应用内安装可以完全避开「安装未知应用」权限与静默升级风险，代价是用户多两步操作。
  - 卖点降级：README 的「无网络权限」改为「联网范围可控」，如实说明只在启动和手动检查时访问 GitHub；对隐私敏感用户，这一改动弱化了原有的「物理隔绝」承诺，属于以可发现性换取的自觉取舍。
  - CI 主机白名单是文本扫描，只能拦住写死的域名，拦不住运行时拼接、重定向或原生库内的请求；它的价值是把「无意中引入新主机」变成构建失败，而不是强保证。
- **影响范围**：`AndroidManifest.xml`、`app/src/main/java/com/gh/daily_trace/{update,domain/update,ui/update}`、`di/Container.kt`、`DailyTraceApp.kt`、`MainActivity.kt`、`ui/settings/*`、`.github/workflows/quality-gate.yml`、`AGENTS.md` 第 1 与第 11 条、`README.md`、`README.en.md`、`docs/{隐私与数据安全,使用手册,常见问题,架构说明,测试指南,发布流程,项目状态与计划}.md`、`变更日志.md`。首个带此能力的发布版本是 `1.0.1`：`1.0.0` 不含检查逻辑，因此 1.0.0 用户不会收到提示，需手动升级一次；从 1.0.1 起才会持续收到后续版本提示。
- **验证方式**：`VersionCompareTest`（12）与 `UpdateResponseTest`（6）覆盖版本比较、`tag_name` 解析与提示节流；`.\scripts\verify.ps1` 全绿（287 用例、lint 0/0、release 构建通过）；AVD 上验证断网静默、发现新版本提示与「稍后」后手动检查（见 `docs/项目状态与计划.md` 批次记录与 `docs/截图/update-01...`）。
